AI杂谈 | 扩散语言模型：当 AI 不再一个词一个词地说出来

过去十年，几乎所有大语言模型都共享同一个骨架：自回归（autoregressive）。模型逐个 token 地往外吐，每个 token 都要等前一个落地才能继续。这套机制简单、稳健、也极其好训，但也留下了一堵墙——你没法同时想十个字，只能一个字一个字地想。

2026 年，这堵墙终于开始松动。一个叫扩散语言模型（Diffusion LLM, dLLM）的技术路线，正在把”写作”变成”改稿”：模型一次性铺开一段画布，然后反复迭代修改，而不是从左到右一条线地往下写。

图：Unsplash 摄影作品，象征扩散模型在画布上反复修订的过程

一、自回归的墙，和”为什么不能一次想十个字”

自回归模型把文本生成建模成条件概率链：(P(y) = \prod_t P(y_t \mid y_{<t}))。每一步都要过一次完整的 Transformer 前向，注意力窗口也天然是因果的。这带来两个硬约束：

  1. 串行依赖：第 100 个 token 的计算必须等第 99 个算完，GPU 矩阵单元吃不饱；
  2. 不可回改：一旦吐出的 token 成了既成事实，后面即使发现它错了，也只能顺着往下圆，无法回头修改。

第二条常被忽略，但恰恰是它让扩散路线显得诱人。人类写作也是”起草—修改—定稿”，而不是”一气呵成永不改稿”。让模型具备可修订性，本质上是让它更像一个作者，而不是一个打印机。

图：Unsplash 摄影作品，象征从粗到细的逐步细化

二、扩散语言模型的基本盘：噪声起步，整体收敛

扩散模型最早成名于图像生成。迁移到文本上，核心思路是把”生成”反转成”去噪”：先在文本位置铺满随机的噪声 token，然后反复多轮迭代，每一轮并行地重新预测所有位置，模型在收敛过程中不断修正局部，直到整段文本”显影”。

这条路线有两个关键分叉：

技术路径 噪声注入方式 已生成 token 能否再改 代表工作
掩码扩散（Masked Diffusion） 用 [MASK] 占位，未确定的位置逐步解掩码 不能，解掩码后即冻结 LLaDA、Dream 系列
均匀状态扩散（Uniform State Diffusion） 用词表中的随机真实 token 替换 能，任意位置都可以在后续轮次被改写 DiffusionGemma

2026 年 6 月 10 日，Google 发布实验性开源模型 DiffusionGemma（Apache 2.0 许可，26B MoE A4B），把后者推到了大众视野。它的做法有几个值得记下的细节：

  • 架构是编码器—解码器 Transformer，权重共享；
  • 初始化不是从零预训练，而是直接拿公开的 Gemma 4 26B A4B MoE 检查点改造——这大幅节省了训练成本，代价是牺牲了一部分绝对生成质量；
  • 生成时先读取一次 prompt 进入 KV Cache，然后初始化一块 256 token 的输出画布，用随机 token 填满，在多轮去噪中并行精修，最后缓存这一块，再开下一块；
  • 官方给出的口径是：在专用 GPU 上文本生成最高 4 倍加速，定位是”速度敏感、交互式本地工作流”，而不是取代自回归模型做高质量生产输出。

Google 官方文档里把这套机制称为 Block Autoregressive Denoising（区块式自回归去噪）：块与块之间仍然是自回归的，但块内部是扩散的。也就是说，并行被塞进了”块”这个更小的粒度里，而不是彻底取消串行。

图：Unsplash 摄影作品，象征并行解码带来的速度与不确定性

三、2026 年的工程竞赛：让扩散真的跑起来

扩散语言模型提出得早，但早期开源 dLLM（LLaDA、Dream）的实际推理速度反而常常慢于同规模自回归模型。原因有两个：一是缺少 KV Cache，二是同时解码多个 token 会显著掉质量。2026 年这一年的工作，几乎全都在补这两个洞。

Fast-dLLM（ICLR 2026，HKU / NVIDIA / MIT） 是其中的代表作。它提出了面向双向扩散模型的块级近似 KV Cache，加上并行解码，在 LLaDA-V 多模态演示上做到最高 10 倍加速。其 v2 版本进一步把吞吐推到：单张 A100 上，batch size 1 时 102.5 tokens/s，batch size 4 时达到 217.5 tokens/s，相比 Qwen2.5-7B-Instruct 有 2.54 倍吞吐优势，GSM8K 得分 60.3，超过了更大的 LLaDA-MoE、Dream 等对比模型。

Orthrus（arXiv:2605.12825）走的是另一条缝合路线：给一个冻结的自回归模型挂一个轻量、可训练的扩散视图。两个视图共享同一份 KV Cache——扩散视图并行起草一段 token，自回归视图负责校验。因为读的是同一批 keys 和 values，就不必再维护一份冗余的草稿缓存，天然是精确的。

PoE-Bridge（ICML 2026）用**乘积专家（Product-of-Experts）**构造一个中间分布，在扩散分布与自回归目标分布之间架桥：扩散模型先并行起草多个候选，再做拒绝采样校验并向中间分布靠拢。论文报告在数学与代码任务上恢复了强模型至少 95% 的准确率，同时生成速度快 2 倍。

DyLLM（arXiv:2603.08026）则从另一个角度省算力：基于显著性做 token 选择，加上部分注意力机制，在 GSM8K、MATH、MBPP、MMLU-Pro 上用不同阈值换取吞吐与精度之间的平衡。

图：Unsplash 摄影作品，象征底层架构的悄然替换

四、现实的冷水：并行不是免费的

这条路上最值得警惕的，是**”理论可并行”与”实际更快”之间的落差**。

UCLA StarAI 团队在 NeurIPS 2025 的自适应并行解码（ADP）论文里给过一组刺眼的数字：Dream 7B 采用随机顺序、256 步解码时，GSM8K 准确率只有 0.404，吞吐 3.31 tokens/s；即便是最保守的左到右顺序，吞吐也只有 10.1 tokens/s——而同一台机器上的 Qwen2.5-7B（自回归）吞吐是 38.6 tokens/s。也就是说，在工程优化到位之前，扩散模型是”能并行但更慢”。

更要命的是质量塌陷。arXiv:2602.23225 指出，标准训练下的推理模型对顺序稳定性有依赖：Dream-7B 在 GSM8K 上用 1024 步时准确率 78.0%，一旦压到 256 步（4 倍并行），准确率直接跌到 46.5%。NAP 方法在同一设定下能维持住表现，恰恰反证了朴素并行化会让长链推理”赶工崩盘”。

而 ParallelBench（ICLR 2026）指出了另一层问题：掩码扩散的自适应采样器无法根据任务难度调整步数——简单任务和地狱级任务用同样的迭代预算，浪费的多余，复杂的不够。这跟软件工程里”永远用同一把锤子敲所有钉子”是同一类毛病。

商业侧的答案则更直接。Inception Labs 的 Mercury 2 把它做成了生产力：扩散式推理模型，宣称吞吐达到 1000 tokens/s，性能对标 Claude 4.5 Haiku 与 GPT-5.2 Mini。这个数字看起来已经甩开主流自回归模型一大截，但要注意口径差异——它比较的是”速度优化的推理模型”，而不是与最强闭源大模型正面比拼。

图：Unsplash 摄影作品，象征工程化落地的日常场景

五、真正的价值，可能不在”更快”

如果只把扩散语言模型理解成”一个更快的解码器”，就低估了它。最实际的收益可能在这三处：

1. 交互式补全。 Google 明确把 DiffusionGemma 定位在”行内编辑、快速迭代、生成非线性文本”这类工作流上。这类场景里，用户会频繁打断和改写，可回改的 token 画布比流式输出更合手。

2. 局部修订而非整段重写。 均匀状态扩散允许模型在后续轮次里推翻已经写下的内容，这在”改一段结构化文本”（表格、配置、代码）时价值明显——自回归模型只能重新生成整段，扩散模型可以只修那几格。

3. 结构化生成的先验优势。 扩散模型本质上在做全局联合分布的迭代优化，而 JSON、表格、分子结构这类强约束输出，恰好更契合”整体协调”的生成方式。

至于”一次多个 token 会掉质量”这个原罪，2026 年的解法基本一致：用自回归模型做校验，用扩散模型做起草。Orthrus、PoE-Bridge、快思考式的拒采样，都是这个范式。某种意义上，扩散语言模型最终可能不是自回归的替代品，而是它的并行起草器。

图：Unsplash 摄影作品，象征多个候选方案被同时评估

六、还没解决的三个问题

训练成本与生态。 DiffusionGemma 靠继承 Gemma 4 的检查点来省训练成本，这说明从头预训练一个高质量 dLLM 依然昂贵。同时，vLLM、Transformers 等推理框架对扩散模型的支持是”实验性”的，工程摩擦会持续存在。

评测体系缺位。 “tokens/s”在自回归模型里几乎等价于用户体验，但在扩散模型里不是——同样的 tokens/s，块大小、去噪轮数、是否开 KV Cache 都会改变结果，跨论文的吞吐数字经常不可比。更麻烦的是，扩散模型不流式输出，首字延迟（TTFT）与总延迟的关系被重写了，用户到底感知到的是”更快”还是”更怪”，还需要新的评测范式。

可靠性与可控性。 一个能同时改写几十个位置的模型，错误也会成片出现：局部改好了，全局一致性却坏了。谷歌自己也承认，自回归 Gemma 4 仍是高质量生产输出的标准，DiffusionGemma 是面向速度敏感场景的实验性模型。这句限定，比任何评测数字都更能说明当前的成熟度。

七、展望：2027 年前后会看到什么

我的判断是三条线会同时推进：

  1. 混合架构成为默认。 区块自回归 + 块内扩散的组合（如 DiffusionGemma 的设计）很可能成为事实标准，因为它是渐进式的：先在一个小块里拿到并行收益，风险可控。
  2. 校验层下沉。 “扩散起草 + 自回归校验”会像早期的 speculative decoding 一样被抽象成通用推理栈里的一个组件，而不是每个团队各写一套。
  3. 可修订性成为独立卖点。 当模型可以回头改，AI 助手的交互形态就会变：从”我写你看”变成”我们一起改”。这件事的影响，也许比吞吐数字大得多。

当然，这一切的前提是能耗与成本。大模型推理的账单已经是一笔不容忽视的开支（此前的行业讨论里，推理成本第一次和训练成本摆在同一张表上）。扩散模型在 batch size 1 的低并发场景里最占便宜，因为它把 GPU 的算力用满了——而这恰恰是个人开发者和小团队最常见的场景。

结语

自回归范式统治了十年，不会因为一篇论文就退场。但它不再是唯一选项了。

扩散语言模型真正带来的，不只是一个更快的解码器，而是把”模型可以回头修改自己的输出”这件事，从奢望变成了工程选项。从 DiffusionGemma 的均匀状态扩散，到 Fast-dLLM 的块级 KV Cache，再到 Orthrus 与 PoE-Bridge 的”起草—校验”范式，2026 年的每一步都在同一条线上：让并行变得便宜，让修订变得可能。

下一步会怎样？值得盯住的三个信号是：下一代主流开源模型是否会默认采用混合解码、推理框架对 dLLM 的支持是否从实验性转为一级公民、以及第一批重度依赖”可修订生成”的生产级应用会出现在哪个行业。

“我们不是要让模型说得更快，而是要让模型想得更完整。”

—— 借用自扩散模型最朴素的那个直觉：先给出全局，再逐轮逼近细节。
